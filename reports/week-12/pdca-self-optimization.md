# PDCA 自优化闭环详解

> 实验周次：第 12 周
> 实验类型：回归检测与自优化闭环

---

## 一、PDCA 核心思想

PDCA = **Plan → Do → Check → Act** 的循环，每一轮都比上一轮更优。

```
┌──────────────┐
│   Plan       │  ← 目标：DELETE QPS ≥ 10,000
│   计划        │     评估方法：cargo test --test qps_benchmark_test
└──────┬───────┘
       │ 设定
       ▼
┌──────────────┐
│   Do         │  ← 行动：实现优化、提交 PR
│   执行        │     工具：cargo, rust, git
└──────┬───────┘
       │ 提交
       ▼
┌──────────────┐
│   Check      │  ← 验证：Gate BP2 + 回归检测
│   检查        │     指标：Δ% QPS、覆盖率
└──────┬───────┘
       │ 判定
       ▼
┌──────────────┐
│   Act        │  ← 改进：根因分析、沉淀知识、规划下一轮
│   改进        │     产物：知识库条目、新基线
└──────┬───────┘
       │ 沉淀
       └─→ 回到 Plan
```

## 二、PDCA 的 4 个关键阶段

### 2.1 Plan（计划）

**任务**：

- 设定下个版本的可度量目标
- 选择评估方法（指标、工具、阈值）
- 明确"完成"的定义

**本实验示例**：

| 项目          | 内容                                    |
| ----------- | ------------------------------------- |
| **目标**      | DELETE QPS ≥ 10,000                    |
| **基线**      | 当前 QPS = 5,000（基线 × 2 即可达标）              |
| **评估方法**    | `cargo test --test qps_benchmark_test` |
| **完成定义**    | CI BP2 通过 + 回归检测 PASS                |

### 2.2 Do（执行）

**任务**：

- 实现优化代码
- 编写单元测试
- 提交 PR
- 跑 CI 验证不破坏现有功能

**本实验示例**：

- PR #500："feat: add WAL buffer for batch DELETE commits"
- 改动：300 行
- 单元测试：12 个新测试
- CI：BP1 静态 + BP2 集成 全部通过

### 2.3 Check（检查）

**任务**：

- 跑 QPS 基准测试
- 与 baseline 对比
- 判定：PASS / WARN / FAIL
- 根因分析（如果失败）

**本实验示例**：

```
OP         Baseline     Current      Δ%        Status
DELETE     5,000        50,000       -900%     PASS (improved)
INSERT     122          125          -2.5%     PASS
SELECT     3,081        3,090        -0.3%     PASS
UPDATE     129          130          -0.8%     PASS
```

**判定规则**（与 `check_regression.sh` 一致）：

- Δ ≤ 5% → PASS（噪声范围内）
- 5% < Δ ≤ 20% → WARN（需说明）
- Δ > 20% → FAIL（必须修复）

### 2.4 Act（改进）

**任务**：

- 记录根因（成功的 OR 失败的）
- 更新知识库（PDCA 的核心价值）
- 决定是否更新 baseline
- 规划下一轮 PDCA

**本实验示例**：

| 产物        | 内容                                          |
| --------- | ------------------------------------------- |
| **根因总结**  | "WAL 缓冲让 DELETE 一次 fsync 覆盖 100 条"             |
| **知识库条目** | `kb/wal-buffer-pattern.md`（可被其他模块复用）           |
| **基线更新**  | baseline DELETE = 5,000 → 50,000（提升 10x）       |
| **下一轮目标** | DELETE QPS ≥ 60,000（再提升 20%）                  |

## 三、PDCA vs 传统"发现问题→修复"

| 维度       | "发现问题→修复"（被动）            | PDCA（主动）               |
| -------- | ----------------------- | ---------------------- |
| 触发方式     | 用户投诉 / 线上事故            | 每次 PR 自动跑              |
| 数据驱动     | 凭经验                    | 量化指标（Δ% / QPS）         |
| 知识沉淀     | 一次性                    | 沉淀到基线 + 知识库            |
| 闭环       | 没有闭环                   | Plan → Do → Check → Act |
| 复盘频率     | 事故后                    | 每次迭代                   |
| 团队参与     | 少数人                    | 全员                     |
| 改进动力     | 防御性（避免再出事）             | 进攻性（持续提升）              |

**一句话总结**：传统是"被动救火"，PDCA 是"主动进化"。

## 四、PDCA 的常见陷阱

### 4.1 Plan 阶段陷阱

| 陷阱           | 反例                       | 正确做法               |
| ------------ | ------------------------ | ------------------ |
| **目标不可度量**   | "提升性能"                   | "DELETE QPS ≥ 10K" |
| **目标太激进**    | "QPS 提升 1000 倍"           | 切分为 3-5 轮，每轮 2-10x |
| **没考虑成本**    | "全面重构"                   | 评估工作量、风险、ROI       |

### 4.2 Do 阶段陷阱

| 陷阱           | 反例             | 正确做法             |
| ------------ | -------------- | ---------------- |
| **跳过测试**     | "我手工试了"       | 必须有单元测试          |
| **改动太大**     | 一次 PR 改 5000 行 | 拆分成小 PR         |
| **没跑 CI**    | "本地能跑就行"      | CI 是唯一权威         |

### 4.3 Check 阶段陷阱

| 陷阱            | 反例           | 正确做法             |
| ------------- | ------------ | ---------------- |
| **只看平均值**     | 平均 QPS 达标就以为成功 | 看 P50/P95/P99 分位数 |
| **只跑一次**      | 跑一次 1 万 QPS   | 至少 3 次取中位数      |
| **不跑回归**      | "新功能怎么可能回归"   | 每次 PR 必跑         |
| **只看 Δ%，不看绝对值** | Δ = 10% 但绝对值只有 5 QPS | 同时看绝对值         |

### 4.4 Act 阶段陷阱（最容易忽略）

| 陷阱          | 反例             | 正确做法                    |
| ----------- | -------------- | ----------------------- |
| **不更新 baseline** | 怕"标准越来越高"     | 显式 `--save-baseline`   |
| **不写知识库**    | "我记得就行"        | 强制写文档                   |
| **不规划下一轮**   | 修完就交差         | 立即设置下一轮目标               |
| **Act 阶段空转**  | "Act = 把文档补完" | Act = 根因 + 知识 + 下一轮目标 |

## 五、PDCA 在本仓库的 3 轮迭代

### 5.1 第 1 轮：DELETE QPS ≥ 10,000

| 阶段    | 内容                                                                 |
| ----- | ------------------------------------------------------------------ |
| Plan  | DELETE QPS ≥ 10,000                                                |
| Do    | 简单索引 + 批量提交                                                       |
| Check | QPS = 5,000（FAIL）→ Δ = -50%（基线 5,000 → 当前 5,000，0%）              |
| Act   | 根因：单条删除 fsync 是瓶颈。引入 WAL 缓冲。                                       |

### 5.2 第 2 轮：DELETE QPS ≥ 50,000

| 阶段    | 内容                                            |
| ----- | --------------------------------------------- |
| Plan  | DELETE QPS ≥ 50,000                           |
| Do    | 引入批量提交 + 异步 WAL                               |
| Check | QPS = 50,000（WARN）→ 5%-20% 区间                  |
| Act   | 根因：DELETE 路径仍有锁竞争。**重写 B+Tree 标记删除**            |

### 5.3 第 3 轮：DELETE QPS ≥ 60,000

| 阶段    | 内容                                              |
| ----- | ----------------------------------------------- |
| Plan  | DELETE QPS ≥ 60,000                             |
| Do    | 重写 B+Tree 标记删除 + WAL                            |
| Check | QPS = 64,000（PASS）→ Δ = +28%（基线 50K → 当前 64K）     |
| Act   | **更新基线 = 64K，沉淀到知识库**，进入维护期                  |

## 六、PDCA 与 Harness 治理的关系

```
Harness 治理的核心 = 让系统自己变好
    │
    ├─ 反馈循环 = PDCA（每轮迭代）
    │   │
    │   ├─ Plan → PRD 提示词（量化目标）
    │   ├─ Do   → 自动化 CI（BP1/BP2/BP3）
    │   ├─ Check → 回归检测（check_regression.sh）
    │   └─ Act   → 知识沉淀（KB / baseline）
    │
    └─ 触发机制
        │
        ├─ 手动：开发者 push
        └─ 自动：CI 失败 / 性能漂移
```

**核心认知**：PDCA 不是"流程"，是"反馈机制"。它让系统能**自我感知、自我调整、自我进化**。

## 八、PDCA 落地的工程清单

要让 PDCA 真正"转起来"，至少需要：

- [ ] **目标量化**：每个优化都有"≥ X 提升"的可度量目标
- [ ] **基线管理**：每次优化达标后显式保存新基线（`--save-baseline`）
- [ ] **自动检测**：每次 PR / 每日定时跑 `check_regression.sh`
- [ ] **失败回环**：FAIL → PR Blocked → 通知 → 修复 → 重跑
- [ ] **知识沉淀**：每次 Act 写一条知识库条目
- [ ] **可视化**：把 Δ% 画成时间序列，让团队看到"曲线"
- [ ] **复盘会**：每 2 周一次 PDCA 复盘，识别跨轮次的共性问题
