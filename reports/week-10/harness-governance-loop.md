## 三、关键数据标注

| 步骤 | 实际做了什么 | 关键数据 | 时间/成本 |
|------|------------|---------|----------|
| ① Issue | 发现 DELETE/UPDATE 性能远低于可用标准 | DELETE 146 QPS, UPDATE 83 QPS | — |
| ② PR #500 | 开发者提交初始实现 | 每次操作后全表写盘 | 开发时间 |
| ③ Gate | BP1 编译通过，BP2 QPS 检查 FAIL | 146 < 10,000 ❌ | 自动化，秒级 |
| ④ 根因分析 | 定位到 `persist_table()` 全表 JSON 序列化 | O(n) 复杂度 | 人工分析，小时级 |
| ⑤ 修复 | 引入 WAL + 批量提交 + 延迟写盘 | 目标 ≥10,000 | 开发时间 |
| ⑥ 知识沉淀 | 更新基准，记录 Pattern | 146 → 10,000+ | 持续积累 |

## 四、"如果 Gate 不存在"对比分析

| 维度 | 有 Gate | 无 Gate |
|------|--------|--------|
| 问题发现阶段 | PR 阶段 | 生产环境 |
| 发现方式 | 自动化 QPS 检查 | 用户投诉/生产事故 |
| 修复成本 | ≈ 1-2 小时 | ≈ 数天 + 数据修复 + 声誉损失 |
| 影响范围 | 仅开发者本人 | 所有用户 |
| 根因分析 | 有基准数据支撑 | 需要紧急排查，压力大 |
| 知识沉淀 | 自动记录 Pattern | 容易重复踩坑 |

## 五、Harness 治理的核心公式

```
Harness 治理 = 提示词层（需求） + 上下文层（信息） + 客观指标（约束）

            ┌─────────────┐
            │  提示词层    │  "优化 DELETE 性能"
            │  （需求）    │  ↓ 必须量化
            └──────┬──────┘     "DELETE QPS ≥ 10,000"
                   │
            ┌──────▼──────┐
            │  上下文层    │  代码实现 + 基准测试数据
            │  （信息）    │  + 存储引擎架构
            └──────┬──────┘
                   │
            ┌──────▼──────┐
            │  Harness层  │  Gate 检查：QPS ≥ 10,000？
            │  （约束）    │  ✅ 通过 / ❌ 拦截
            └─────────────┘
```
